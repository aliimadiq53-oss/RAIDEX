# فصل واجهات وروابط المستخدمين حسب الدور

مهم جداً:

لا أريد أن يدخل جميع المستخدمين إلى نفس Dashboard ثم تختلف الصلاحيات فقط.

أريد لكل نوع مستخدم:

* رابط مستقل.
* صفحة دخول مستقلة أو بوابة واضحة.
* واجهة مستقلة.
* وظائف محددة جداً.
* Navigation مختلفة حسب الدور.

جميع هذه الواجهات تتصل بنفس النظام ونفس قاعدة البيانات ونفس الـAPI، لكن تجربة الاستخدام منفصلة تماماً.

---

# 1. رابط الحكم

مثال:

`/judge`

أو:

`judge.domain.com`

الحكم لديه:

* Username خاص.
* Password خاص.
* حساب Judge خاص به.

بعد تسجيل الدخول لا يدخل إلى Admin Dashboard.

يدخل مباشرة إلى:

# واجهة الحكم

ولا يرى أي شيء آخر غير الوظائف المطلوبة له.

---

# واجهة الحكم

يجب أن تكون شديدة البساطة.

لا Sidebar.

لا Dashboard.

لا إحصائيات.

لا قائمة لاعبين كاملة.

لا إدارة بطولة.

لا Users.

لا Settings.

لا نتائج عامة.

لا Live Control.

فقط:

شعار AL AFANDI.

اسم البطولة الحالية.

اسم الجولة.

اسم الحكم.

ثم حقل كبير جداً:

# رقم المشاركة

يكتب الحكم مثلاً:

**14**

ثم:

**بحث**

بعد البحث يظهر فقط:

* اسم اللاعب.
* رقم المشاركة.

ثم:

* الوقت.
* الأخطاء.
* إرسال النتيجة.

وتحتها الإجراءات المسموحة مثل:

* استبعاد.
* حظر.

إذا كانت الصلاحية موجودة.

هذه الصفحة يجب أن تبدو مثل أداة تشغيل سريعة، وليست Dashboard.

---

# 2. رابط مدخل البيانات

مثال:

`/data-entry`

أو:

`data.domain.com`

مدخل البيانات لديه Username وPassword خاصان به.

بعد تسجيل الدخول يدخل مباشرة إلى:

# لوحة مدخل البيانات

ولا يرى لوحة Admin الكاملة.

---

# صفحة مدخل البيانات

تعرض فقط الوظائف المسموحة له مثل:

* البحث عن لاعب.
* إضافة لاعب.
* تعديل بيانات لاعب حسب الصلاحية.
* إضافة مشارك إلى بطولة.
* تحديد رقم المشاركة.
* اختيار الخيل.
* إدخال أو تحديث البيانات الأساسية.
* مشاهدة البطولات التي تم تعيينه عليها.

لا يرى:

* إدارة المستخدمين.
* الصلاحيات.
* إعدادات النظام.
* Audit Log الكامل.
* إعدادات الموقع الحساسة.
* إزالة الحظر.
* اعتماد النتائج.
* Live Control.

إلا إذا أعطي صلاحية خاصة بشكل صريح.

---

# شاشة مدخل البيانات الرئيسية

اجعلها عملية جداً.

في الأعلى:

اسم المستخدم.

البطولة المحددة.

ثم:

حقل بحث كبير:

**ابحث عن لاعب بالاسم أو رقم اللاعب**

ثم إجراءات واضحة:

**إضافة لاعب جديد**

**إضافة لاعب موجود إلى البطولة**

**عرض المشاركين**

**إدخال بيانات المشاركة**

---

# 3. رابط Admin

مثال:

`/admin`

أو:

`admin.domain.com`

Admin لديه واجهة مستقلة وكاملة.

بعد تسجيل الدخول يدخل إلى:

# Admin Dashboard

وهي الواجهة الإدارية الرئيسية.

---

# صلاحيات Admin

حسب الصلاحيات يمكنه الوصول إلى:

* Dashboard.
* البطولات.
* اللاعبين.
* المشاركين.
* الخيول.
* الحكام.
* مدخلي البيانات.
* المستخدمين.
* Roles & Permissions.
* Tournament Rulesets.
* الجولات.
* الأخطاء.
* النتائج.
* اعتماد النتائج.
* Live Control.
* الحظر.
* إزالة الحظر.
* إدارة الموقع.
* Audit Log.
* الإعدادات.

---

# 4. رابط التحكم المباشر

يمكن أن يكون داخل Admin أو برابط مباشر خاص للمستخدم المخول.

مثال:

`/live-control`

هذا الرابط لا يكون متاحاً للحكم.

يكون فقط لـ:

Admin

أو مستخدم لديه صلاحية:

**Live Display Control**

ويستخدم أثناء البطولة للتحكم بما يظهر على الشاشة العامة.

---

# 5. رابط شاشة العرض

أنشئ رابطاً مستقلاً للشاشة الكبيرة.

مثال:

`/display`

أو:

`/live-screen`

هذه الصفحة:

لا تحتوي Login عادي للمستخدم النهائي إذا كان النظام يؤمنها بطريقة مناسبة.

لا تحتوي Sidebar.

لا تحتوي أزرار Admin.

لا تحتوي Navigation.

هي فقط شاشة عرض Full Screen.

يعرض عليها المحتوى الذي يرسله Admin من Live Control.

---

# 6. Public Website

الموقع العام يبقى منفصلاً.

مثال:

`domain.com`

وهو للجمهور.

لا يظهر فيه النظام الإداري.

لا يظهر فيه Judge Portal.

لا يظهر فيه Data Entry.

الدخول الإداري يكون من روابط منفصلة.

---

# 7. Login مستقل حسب البوابة

أريد تصميم Login مختلف قليلاً حسب البوابة مع المحافظة على نفس هوية AL AFANDI.

مثلاً:

## Judge Login

عنوان:

**دخول الحكم**

Username

Password

دخول

---

## Data Entry Login

عنوان:

**دخول مدخل البيانات**

Username

Password

دخول

---

## Admin Login

عنوان:

**دخول الإدارة**

Username / Email

Password

دخول

---

# 8. إذا حاول مستخدم دخول رابط غير مخصص له

مثال:

Judge حاول فتح:

`/admin`

لا تعرض له Admin Dashboard ناقصة.

بل اعرض:

**ليس لديك صلاحية للوصول إلى هذه الصفحة**

ثم زر:

**العودة إلى لوحة الحكم**

وبالعكس:

Data Entry إذا حاول دخول صفحة Admin حساسة يتم منعه تماماً.

---

# 9. التوجيه بعد Login

يجب أن يعتمد النظام على Role.

مثلاً:

Judge
→ `/judge`

Data Entry
→ `/data-entry`

Admin
→ `/admin`

Live Control User
→ `/live-control`

لا تجعل المستخدم يختار لوحته بعد تسجيل الدخول إذا كان لديه Role واحد فقط.

---

# 10. مستخدم لديه أكثر من Role

إذا كان شخص واحد لديه أكثر من Role فعلياً، يمكن بعد تسجيل الدخول أن يظهر له:

**اختر مساحة العمل**

مثلاً:

الإدارة

الحكم

لكن هذه حالة خاصة.

الوضع الطبيعي:

كل مستخدم يدخل مباشرة إلى البوابة الخاصة به.

---

# 11. فصل Navigation

كل Portal لديه Navigation خاصة.

## Judge

لا Navigation تقريباً.

فقط:

النتيجة الحالية.

Logout.

---

## Data Entry

Navigation بسيطة:

الرئيسية.

اللاعبون.

المشاركون.

البطولات المخصصة.

Logout.

---

## Admin

Navigation كاملة.

---

# 12. الفكرة التقنية

صمم الـUX على أساس أن النظام يحتوي عدة Portals:

### Public Portal

للجمهور.

### Admin Portal

للإدارة.

### Judge Portal

للحكام.

### Data Entry Portal

لمدخلي البيانات.

### Live Control Portal

للتحكم بالعرض.

### Live Display

للشاشة العامة.

كلها تستخدم نفس Backend وAPI وقاعدة البيانات، لكن لها Routes وواجهات وصلاحيات مستقلة.

---

# 13. المطلوب من النظام

أضف Screens منفصلة لهذه البوابات:

**Judge Login**

**Judge Portal**

**Data Entry Login**

**Data Entry Dashboard**

**Admin Login**

**Admin Dashboard**

**Live Control**

**Public Live Display**

ولا تعيد استخدام Admin Dashboard كواجهة للحكم أو مدخل البيانات.

المطلوب هو:

# Role-Specific Experience

لكل مستخدم واجهة تناسب مهمته فقط.
